# Progress graphs: correctness and plotting review

Source review, 8 September 2026. This expands the chart findings already in the UI/deep audits. It does not describe a running Flutter screenshot. The existing chart library is not the primary problem; data semantics, formatting and interaction need correction before changing libraries.

## Verdict

The charts have a useful foundation: Week/Month/6M date windows, actual calendar x positions, borderless plot frames, zero-baseline short-range step bars, support for goal references, and some handling of missing dates. Retain these foundations. The charts are not ready to sign off because several decisions can misrepresent the user's history.

## Recommended plots by metric

| Metric | Week / Month | Six months | Hero and inspection |
|---|---|---|---|
| Weight | Visible measured dots; optional clearly named calendar trend; minimal or no area fill | Sparse measured dots plus a documented trend; do not force all observations into daily continuity | Latest measurement and its date; trend change with sample count; kg/lb everywhere |
| Body fat | Measurement dots and a restrained trend only with sufficient observations | Same sparse-measurement approach | Latest %, and change in **percentage points**, not ambiguous relative percent |
| BMI | Derived measurement dots; muted supplementary metric | Optional trend using valid underlying weight/height inputs | Unitless value with calculation context; unavailable if inputs invalid; avoid diagnostic claims |
| Steps | Daily bars, zero baseline, visible target reference | Calendar-week **average daily steps on recorded days**, with n/7 coverage; disclose partial weeks | Average/day, total recorded steps, recorded days; selected date/value/source |
| Sleep | Nightly duration bars or dots; configured target reference | Weekly recorded-night averages with coverage | Average recorded night; tooltip as 7 h 30 min; define which date owns an overnight session |
| Calories | Daily bars from logged meals; clearly identify incomplete days | Weekly average **logged** calories/day, with coverage | Logged intake, not asserted actual intake; optional target and meal completeness |
| Protein | Daily bars with configured protein target | Weekly average logged protein/day with coverage | g/day and clear logged-data qualification |
| Screen time | Daily duration bars, zero baseline | Weekly recorded-day average with coverage | h/min; configured limit; no-data and denied permission distinct from zero |
| Habit completion | Seven fixed 0–100% bars with numerator/denominator on selection | Weekly eligible-occurrence completion or a heatmap for calendar consistency | “3/4 scheduled habits”; rest/not-scheduled/future separate |

Do not label a weekly sum as a daily average. ## Visual and interaction direction

Use a borderless filled surface with the same type, spacing and radius as the rest of Sthira. Keep the chart visually quieter than the important number. Three or four faint horizontal reference lines are enough; these are data-reading guides, not decorative card borders. If strict no-grid styling is preferred, retain readable y labels and a goal reference where relevant.

Above the plot: metric picker, visible Week/Month/6M selector, date range and correctly labeled hero. Below it: recorded-day coverage and two or three meaningful statistics. Avoid estimated calorie-burn/distance circles dominating the Steps graph: the current fixed multipliers are rough estimates derived from average steps, not independently observed metrics. If retained, label both the estimate and its daily basis.

Tap or drag to inspect a point without leaving the screen. Use one active marker/date guide and a compact readout containing date, value, unit and manual/synced status where available. Offer an explicit View day action. Provide a textual/table alternative and keyboard/screen-reader access to the same observations. Avoid haptics on every scrubbed point; optional feedback on deliberate selection is sufficient.

Allow a subtle 150–200 ms crossfade between ranges/metrics, but do not morph unrelated dates into a continuous story or replay all points. Keep selected values immediate. Empty, one-point, all-zero, sparse and partial-period plots should be first-class states.

## Acceptance fixtures

1. Observed steps `[0, 8000]` and five missing days: average 4,000 across two recorded days, with a visible zero versus missing distinction.
2. Seven weigh-ins spaced a week apart: do not call their combined average a seven-day trend.
3. Month data only on days 1, 2 and 20: no unlabeled observed-data line through days 3–19, including the trend overlay and 6M view.
4. Goal 60 kg with observations 80.0–80.5 kg: variation remains readable and goal visibility is accurately communicated.
5. Every metric/unit combination: correct tooltip, goal-difference and summary format; kg/lb conversion exactly once.
6. Log/edit/delete a meal while Progress is open: plotted nutrients and summary refresh.
7. Month starting midweek, month with 28/29/30/31 days, six-month span crossing a year: correct tick anchors and period labels.
8. Six-month average with two recorded days in one week and seven in another: both display their own coverage, and any overall average weights actual observations correctly.
9. Tap/drag selects without navigation; View day navigates intentionally; range switching is visible and usable.
10. Reduced motion, 320/360/412 logical widths, large text, one value, constant values, all missing, observed zero and future slots: no misleading marks, overflow or invented progress.

The companion plotting prompt and labeled browser proposal make these requirements reviewable. Native screenshots and rendering tests remain implementation acceptance work.
